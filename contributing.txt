## Problem Statement

Renewable energy generation is inherently intermittent. Solar output falls when
clouds pass or after sunset; wind generation fluctuates with wind speed. Grid
operators must simultaneously forecast demand spikes, monitor a mixed fleet of
renewable assets for anomalies, diagnose root causes, and balance power flow
across regions — all under time pressure, with incomplete information, and
using tools that were not designed to work together.

The result is unnecessary renewable-energy curtailment, revenue loss, delayed
corrective maintenance, and avoidable grid instability.

intelligent modules:

  1. Demand Spike Forecasting  — 12h/24h/7-day predictions with confidence

# Problem Statement

## Domain
Grid Load Optimisation & Renewable Energy Performance Advisory

## Core Problem
Renewable generation is intermittent by nature:
  - Solar output drops when clouds pass or after sunset
  - Wind output changes with wind speed
  - Battery charge levels fluctuate based on charging cycles

Grid operators currently face four compounding challenges simultaneously:

  1. DEMAND FORECASTING — Predicting when electricity demand will spike
     (morning industrial ramp-up, midday commercial HVAC, evening EV charging)
     with enough lead time to prepare additional generation or storage.

  2. ANOMALY DETECTION — Identifying when an individual renewable asset is
     underperforming relative to what weather/conditions suggest it should
     produce. Without early detection, losses compound for hours unnoticed.

  3. ROOT CAUSE DIAGNOSIS — Determining WHY an asset is underperforming
     (yaw misalignment, blade erosion, inverter fault, soiling, cell imbalance,
     etc.) so maintenance can be targeted correctly.

  4. LOAD BALANCING — Deciding which inter-regional power transfers, storage
     dispatch actions, or curtailments to execute and in what order of priority.

## Impact of the Problem
  - Unnecessary renewable energy curtailment (47+ MW estimated in prototype)
  - Revenue loss (£24,000+ per 6-hour window in prototype estimates)
  - Delayed corrective maintenance due to missed early detection
  - Grid instability from poor load-balancing decisions
  - Operator fatigue from managing disparate, unconnected tools

## Why Existing Solutions Fall Short
  - Enterprise SCADA/EMS systems are expensive and siloed
  - Alerts are reactive, not predictive
  - Root cause analysis is manual and expert-dependent
  - Load-balancing recommendations are not ranked or explained

# Solution Overview

## What We Built
EnergyOS is an AI-powered single-page web application that gives grid operators
a unified intelligence platform. It combines five modules into one workflow:

## Module 1 — Operations Dashboard
Real-time overview of all renewable assets and the grid.
  - 4 live KPI cards (Total Generation, Grid Demand, Active Anomalies,
    Curtailment Risk)
  - 24-hour demand vs renewable supply chart
  - Generation mix doughnut chart (Wind / Solar / Hydro / Battery)
  - Per-asset health tiles with efficiency bars and status badges
  - Live event feed of alerts and actions
  - Regional load distribution bars
  - 6-hour demand outlook mini-chart

## Module 2 — Demand Spike Forecasting
AI-driven load prediction with confidence intervals.
  - 12h / 24h / 7-day forecast windows
  - Forecast vs historical demand chart with confidence bands
  - Model accuracy trend (MAPE / RMSE) over last 7 days
  - Spike event list with severity and cause explanation
  - Hourly forecast table with risk classification
  - Weekly demand pattern comparison
  - Spike probability distribution by hour of day
  - Forecasted generation mix (stacked by source type)

## Module 3 — Load Balancing Engine
Automated recommendations for optimal inter-regional power flow.
  - Regional load vs capacity bar chart (colour-coded: over/normal/under)
  - Grid health radar (Stability, Efficiency, Balance, Resilience,
    Renewables %, Forecast Accuracy)
  - Grid load trend over last 24 hours
  - Curtailment history stacked by region (last 7 days)
  - Prioritised action list with one-click Approve
  - Regional import/export chart
  - Asset dispatch schedule table
  - Dispatch by asset type (Current vs Scheduled MW)
  - Regional renewable share chart

## Module 4 — Anomaly Detection
ML-powered detection of performance deviations.
  - 4 KPI cards (Total Anomalies, Critical Alerts, Active Monitoring,
    Avg Confidence)
  - Anomaly severity trend (stacked bar: Critical/High/Medium, last 7 days)
  - Detection confidence histogram
  - Filterable anomaly table (All / Critical / High / Medium)
  - Per-anomaly detail panel with asset info, deviations, and actions
  - Performance time series with expected vs actual overlay
  - Detection method performance (Precision & Recall: 5 algorithms)
  - Anomaly distribution by asset type
  - Deviation vs Confidence scatter plot
  - Anomaly count by hour of day (24-hour rolling)

## Module 5 — Root Cause Analysis
Automated fault tree analysis per underperforming asset.
  - Asset health status doughnut (Optimal / Degraded / Critical)
  - Cause probability radar by fault type
  - Asset efficiency comparison bar chart with 92% target line
  - Per-asset RCA cards: efficiency, output, fault tree, recommendation
  - Cause category distribution chart
  - Asset type vs average efficiency chart
  - Output vs capacity per asset (colour-coded by performance ratio)
  - Fleet efficiency trend over last 7 days

## Module 6 — Operator Brief
Auto-generated integrated brief for operators.
  - 4 KPI cards (Peak Demand, Curtailment Risk, Revenue at Risk,
    Recovery Potential)
  - Fleet status doughnut overview
  - Curtailment risk by asset bar chart
  - Executive summary (period, peak demand, active anomalies, spikes,
    curtailment risk, estimated revenue loss)
  - Critical anomalies section with severity alerts
  - Curtailment minimisation plan (current MW → target MW → estimated saving)
  - Priority load-balancing actions list
  - Demand forecast vs available capacity chart (next 12h)
  - Energy recovery by asset chart
  - Action timeline (Immediate → Tonight)
  - Estimated revenue impact by action
  - Anomaly type breakdown doughnut

## How IBM Bob Was Used
  IBM Bob was used as the AI pair-programming assistant throughout development:
  - Generating and iterating on the module JavaScript architecture
  - Debugging Chart.js rendering issues (stacked bar, mixed types, canvas sizing)
  - Writing and fixing the chart wrapper library (charts.js)
  - Cross-referencing all 36 canvas IDs against 47 DOM references for validation
  - Reviewing and completing all submission and documentation files

# Technical Architecture

## Overview

EnergyOS is a fully client-side Single Page Application (SPA).
No backend server, no API calls, no database. All data is synthetic.

## Architecture Diagram

  ┌─────────────────────────────────────────────────────────────┐
  │                        Browser                              │
  │                                                             │
  │  ┌──────────┐    fetch()    ┌─────────────────────────────┐ │
  │  │index.html│ ─────────────▶│  Page Fragments (.html)     │ │
  │  │(app shell)│              │  dashboard / forecast /      │ │
  │  │          │               │  loadbalancer / anomaly /    │ │
  │  └────┬─────┘               │  rootcause / brief           │ │
  │       │                     └──────────────┬──────────────┘ │
  │       │                                    │ innerHTML       │
  │  ┌────▼─────────────────────────────────────▼──────────────┐ │
  │  │                    app.js (SPA Router)                   │ │
  │  │  navigate(pageId) → fetch(html) → rAF → module.init()   │ │
  │  └────────────────────────┬────────────────────────────────┘ │
  │                            │                                  │
  │       ┌────────────────────┼────────────────────┐            │
  │       ▼                    ▼                    ▼            │
  │  ┌─────────┐         ┌──────────┐         ┌─────────┐       │
  │  │ data.js │         │charts.js │         │modules/ │       │
  │  │         │         │          │         │         │       │

  │  │         │         │scatter() │         │brief    │       │
  │  │ASSETS[] │         │stacked   │         │         │       │

  │  └─────────┘         └──────────┘                           │
  │                            │                                  │

  │                       │  4.4.0  │                            │
  │                       └─────────┘                            │
  └─────────────────────────────────────────────────────────────┘

## Data Flow
  EnergyData (data.js)
    → seeded rand() generates: demand history, forecasts, anomalies,
      load distribution, root causes, operator brief
    → consumed by module.init() via EnergyData.* API calls
    → chart data passed to Charts.* wrapper functions
    → Charts.* calls new Chart(canvas, config) via Chart.js 4.4

## SPA Routing
  app.js maintains a page registry mapping pageId → {file, module}.
  navigate(pageId):
    1. Show loader
    2. fetch(page.file) → inject into #mainContent
    3. Charts.destroyAll() — prevents canvas reuse errors
    4. requestAnimationFrame → requestAnimationFrame → module.init()
       (double rAF guarantees CSS layout before Chart.js measures containers)

## Chart Rendering
  .chart-wrap { position: relative; height: 240px; }
  .chart-wrap canvas { position: absolute; width: 100%; height: 100%; }
  All charts: maintainAspectRatio: false — fills container exactly.
  Chart types used: line, bar, stackedBar (bar+stacked:true),
                    doughnut, radar, scatter

## Module Pattern
  Each module is an IIFE returning { init, ...publicMethods }:
  const XModule = (() => {
    function init() { /* render KPIs, charts, tables, bind events */ }
    return { init };
  })();

## File Count
  HTML pages:   7  (index + 6 page fragments)
  CSS files:    3  (main, components, dashboard)
  JS core:      3  (data, charts, app)
  JS modules:   5  (forecast, loadbalancer, anomaly, rootcause, brief)
  Total charts: 36 canvas elements, 33 chart instances

# Setup Guide

## Prerequisites
  - A modern web browser (Chrome 90+, Firefox 88+, Edge 90+, Safari 14+)
  - Python 3 OR Node.js (for local HTTP server)
  - No npm install, no build step, no environment variables required

## Option A — Python (Recommended, Zero Setup)

  Step 1: Clone the repository
    git clone https://github.com/[your-org]/bob-ai-hackathon-energy-optimizer.git
    cd bob-ai-hackathon-energy-optimizer

  Step 2: Start the HTTP server from the src/ directory
    cd src
    python -m http.server 8080

  Step 3: Open the app
    Open your browser and go to: http://localhost:8080

  Expected: EnergyOS loads with the Operations Dashboard visible.
  All 6 pages accessible via the left sidebar navigation.

## Option B — Node.js (npx serve)

  Step 1: Clone the repository (same as above)

  Step 2: Serve from src/
    cd src
    npx serve .

  Step 3: Open the URL shown in the terminal (usually http://localhost:3000)

## Option C — VS Code Live Server

  Step 1: Install the "Live Server" extension in VS Code
  Step 2: Open the energy-optimizer/ folder in VS Code
  Step 3: Right-click src/index.html in the file explorer
  Step 4: Select "Open with Live Server"
  Expected: Browser opens automatically to the running app

## IMPORTANT — Why a Server is Required

  EnergyOS uses fetch() to load page HTML fragments dynamically.
  Opening src/index.html directly as a file:// URL will trigger CORS errors
  and the pages will not load. You MUST serve over HTTP (any method above).

## Navigating the App

  Left sidebar:
    Dashboard          — Live KPIs, charts, asset health grid, event feed
    Demand Forecast    — Forecasting with confidence bands, spike events
    Load Balancing     — Regional load, grid radar, approve actions
    Anomaly Detection  — ML anomaly table, time-series, scatter charts
    Root Cause Analysis— Per-asset fault trees, efficiency charts
    Operator Brief     — Auto-generated executive brief with all charts

  Top bar:
    Refresh button     — Reseeds all synthetic data and redraws charts
    Alert badge        — Shows count of active anomalies

## Verifying Everything Works

  Checklist after opening the app:
  [ ] Dashboard loads with 4 KPI cards populated
  [ ] "Live Grid Demand" chart shows data (not an empty panel)
  [ ] "Generation Mix" doughnut chart shows Wind/Solar/Hydro/Battery
  [ ] Clicking "Demand Forecast" in sidebar loads that page with charts
  [ ] Clicking "Load Balancing" shows Regional Load bar chart + radar
  [ ] Clicking "Anomaly Detection" shows the anomaly table with 5 rows
  [ ] Clicking a table row shows the Anomaly Detail panel on the left
  [ ] Clicking "Root Cause Analysis" shows per-asset RCA cards
  [ ] Clicking "Operator Brief" shows the full brief with sections filled
  [ ] "Refresh" button in top bar reloads all data

## Troubleshooting

  Issue: Blank page / "Page Load Error" alert
  Fix:   Make sure you are serving from src/ over HTTP, not opening as file://

  Issue: Charts appear but are empty (no data)
  Fix:   Hard refresh the browser (Ctrl+Shift+R / Cmd+Shift+R) to clear cache

  Issue: Page loads but some chart panels are blank
  Fix:   Click the Refresh button in the top bar to re-initialise all modules

  Issue: "Cannot load ../pages/dashboard.html"
  Fix:   Confirm your HTTP server root is src/ (not the project root)

## No Environment Variables Required
  All data is synthetically generated in src/assets/js/core/data.js.
  There are no API keys, no .env files, no external service dependencies.
  The app works fully offline once loaded.

  analysis, load balancing, and operator briefs into a single client-side SPA.

  The platform features 36 interactive charts across 6 pages, all fully
  populated with meaningful synthetic data. Every module renders KPI cards,
  data tables, and multiple chart types (line, bar, stacked bar, doughnut,
  radar, scatter) — giving operators a complete, data-rich view of their
  renewable energy fleet at all times.

How to run:
  cd src && python -m http.server 8080
  Open http://localhost:8080
